# Лабораторна робота №1: Розгортання Web-сервісу з автоматизацією

## 1. Індивідуальне завдання (Варіант)
Номер студента у списку групи: **N = 12**.

Розрахунок варіанту:
* **V2** = (12 % 2) + 1 = 1 (Конфігурація: Аргументи командного рядка; БД: MariaDB)
* **V3** = (12 % 3) + 1 = 1 (Тематика застосунку: Notes Service)

**Завдання:** Розробити веб-застосунок "Notes Service" (зберігання текстових нотаток) на базі MariaDB. Застосунок має конфігуруватися виключно через аргументи командного рядка, працювати локально на порту 3000 та бути схованим за reverse-proxy (Nginx).

## 2. Документація веб-застосунку
**Призначення:** Сервіс `mywebapp` призначений для створення, зберігання та перегляду текстових нотаток.

**Стек технологій:**
* Backend: Node.js, Express
* База даних: MariaDB (драйвер `mariadb`)
* Взаємодія: REST-подібне API з підтримкою Content-Negotiation (HTML/JSON) залежно від заголовка `Accept`.

**Локальне середовище (Розробка/Тестування):**
1. Встановіть Node.js (v20+) та MariaDB.
2. Виконайте `npm install` у директорії `app/`.
3. Створіть базу даних та виконайте міграцію з файлу `db/init.sql`.
4. Запустіть застосунок командою (приклад):
   ```bash
   node app/server.js --port=3000 --db-host=127.0.0.1 --db-user=root --db-pass=mypass --db-name=notes_db
## 3. API Ендпоінти
Застосунок підтримує повернення даних у форматах `application/json` або `text/html` (залежно від заголовка `Accept`).

* `GET /` — Кореневий ендпоінт. Повертає виключно `text/html` зі списком доступних API.
* `GET /notes` — Отримати список усіх нотаток (повертає масив об'єктів з полями `id`, `title`).
* `POST /notes` — Створити нову нотатку. Очікує JSON body: `{"title": "string", "content": "string"}`.
* `GET /notes/<id>` — Отримати повний вміст нотатки за її ID (`id`, `title`, `content`, `created_at`).
* `GET /health/alive` — Перевірка Liveness (завжди повертає HTTP 200 OK).
* `GET /health/ready` — Перевірка Readiness (перевіряє з'єднання з БД, повертає 200 OK або 500 Error). Заблоковано ззовні через Nginx.

## 4. Документація по розгортанню

**Базовий образ віртуальної машини:** Для розгортання використовується офіційний образ **Ubuntu Server 22.04 LTS (Jammy Jellyfish)**.

**Вимоги до ресурсів ВМ:**
* CPU: 1 Core (мінімум)
* RAM: 1 GB (рекомендовано 2 GB для коректної роботи Node.js та npm)
* Disk: 10 GB
* Network: Доступ до мережі Інтернет для завантаження пакетів (NAT) та прокинутий порт 80 для доступу до веб-сервісу на хості.

**Вхід на ВМ:**
* Підключення здійснюється через SSH або Console.
* Credentials за замовчуванням (залежить від налаштувань інсталятора Ubuntu): користувач `ubuntu`. Після виконання автоматизації цього користувача буде заблоковано.

**Як запустити автоматизацію розгортання:**
1. Зайдіть на чисту ВМ Ubuntu.
2. Склонуйте цей репозиторій:
   ```bash
   git clone <URL_ВАШОГО_РЕПОЗИТОРІЮ>
   cd <НАЗВА_ПАПКИ_РЕПОЗИТОРІЮ>
   ```
3.  Запустіть скрипт автоматизації з правами адміністратора:
    ```bash
    sudo bash deploy/setup.sh
    ```
## 5. Інструкція з тестування розгорнутої системи

Після успішного виконання скрипта `setup.sh`, перевірте систему за такими критеріями:

1. **Доступність веб-сервісу:**
   Відкрийте в браузері IP-адресу вашої віртуальної машини (наприклад, `http://<VM_IP>/`). Має відкритися HTML-сторінка зі списком API.
2. **Перевірка Nginx (Reverse Proxy):**
   Спробуйте перейти за адресою `http://<VM_IP>/health/alive`. Nginx має повернути помилку `403 Forbidden` (доступ до системних ендпоінтів ззовні закрито).
3. **Перевірка користувачів та прав:**
    * Спробуйте увійти за користувача `teacher` з паролем `12345678`. Система має негайно запросити зміну пароля.
    * Увійдіть під користувачем `operator` (пароль `12345678`, також вимагає зміни).
    * Виконайте команду `sudo systemctl restart mywebapp` — вона має пройти без запиту пароля.
    * Виконайте команду `sudo rm -rf /` (або іншу адміністративну команду) — система має відмовити в доступі користувачу `operator`.
4. **Перевірка бази даних:**
   Переконайтеся, що створення нотаток працює коректно, відправивши POST-запит на `http://<VM_IP>/notes`.

## 🐳 Запуск проєкту за допомогою Docker Compose (Лабораторна робота №2)

Цей проєкт повністю контейнеризовано. Усі компоненти системи (Node.js застосунок, Nginx як Reverse Proxy та база даних MariaDB) налаштовані для спільного автоматичного розгортання в ізольованій Docker-мережі. Дані бази даних зберігаються на постійному томі (persistent volume).

### Попередні вимоги
Для запуску проєкту на вашому комп'ютері мають бути встановлені:

2. Виконайте команду для збірки образів та запуску контейнерів у фоновому режимі:
   ```bash
   docker-compose up -d --build
3. Дочекайтеся завершення збірки та статусу `Started` для всіх трьох контейнерів (`lab-mariadb`, `lab-nodejs-app`, `lab-nginx`).
4. Відкрийте браузер та перейдіть за адресою:
   http://localhost:3000 
### Корисні команди
- Перегляд логів застосунку:

   ```bash
   docker-compose logs app
   ```
- Зупинка всіх сервісів:
Щоб зупинити роботу серверів та видалити контейнери (при цьому дані бази даних залишаться збереженими на диску), виконайте:

   ```bash
   docker-compose down
   ```

# Лабораторна робота №4: IaC. Terraform. Ansible.

Цей проєкт демонструє практичне застосування принципів декларативного керування інфраструктурою та конфігурацією багатовузлових систем. Застосунок розгорнуто в розподіленій архітектурі на двох окремих віртуальних машинах в межах однієї мережі.


## Загальна архітектура системи

Система розділена на два функціональні вузли для забезпечення ізоляції та безпеки:
* **VM1 (worker):** Приймає зовнішній трафік через веб-сервер **Nginx (Reverse Proxy)** на порту `80`. Nginx перенаправляє запити всередину машини на локальний **Node.js веб-застосунок**, що працює на порту `3000`.
* **VM2 (db):** На базі цієї машини розгорнуто **SQL базу даних MariaDB**. 

### Мережеві обмеження та безпека:
Доступ до порту бази даних (`3306`) жорстко обмежений на рівні системного фаєрвола UFW. Пряме підключення ззовні заблоковане — база приймає пакети **тільки** з віртуальних машин `db` та `worker`.

---

## Інструкція із запуску системи

Розгортання та налаштування середовища повністю автоматизоване й відбувається у 2 етапи:

### Етап 1: Автоматизація інфраструктури (Terraform) 
Створення двох ВМ на базі офіційного Cloud-образу Ubuntu виконується за допомогою провайдера `libvirt` (QEMU/KVM). Також на цьому етапі через `cloud-init` автоматично підкидається SSH-ключ для доступу.
   
   ```bash
   cd terraform
   terraform init
   terraform apply
   ```

### Етап 2: Управління конфігурацією (Ansible)

Накат конфігів, встановлення пакетів та деплой коду виконуються ідемпотентно й декларативно, без використання сирих shell-команд.

1. Перейдіть у робочу директорію Ansible:
```bash
   cd ../ansible
```

2. Переконайтеся, що у файлі статичного інвентаря `hosts.ini` прописані актуальні IP-адреси створених машин, розділені на відповідні групи `[workers]` та `[db]`.

3. Запустіть сценарій конфігурації:
```bash
ansible-playbook site.yml
```

## 🧪 Валідація та перевірка (Health Checks)

Для перевірки успішності налаштування розподіленої інфраструктури, коректності роботи веб-сервера Nginx, застосунку та мережевих обмежень використовуйте такі команди (виконуються через `curl` або SSH):

### 1. Перевірка Reverse Proxy (Nginx)
Запит на зовнішню IP-адресу першої віртуальної машини (VM1 worker) на стандартний порт 80 має перенаправлятися на локальний порт застосунку й повертати відповідь:
```bash
curl http://<VM1_WORKER_IP>/
```
Очікуваний результат: `Hello from KPI Worker Node!`

### 2. Alive Check (Статус працездатності застосунку)
Перевірка базового ендпоінту моніторингу, який віддає поточний статус роботи самого веб-застосунку:  
```bash
curl http://<VM1_WORKER_IP>/health/alive
```
Очікуваний результат: `OK `  

### 3. Ready Check (Перевірка наскрізного зв'язку з БД)
Перевірка статусу готовності, яка в реальному часі верифікує наявність коректного мережевого зв'язку та доступу між веб-застосунком на VM1 (worker) та базою даних MariaDB на VM2 (db):
```bash
curl http://<VM1_WORKER_IP>/health/ready
```
Очікуваний результат: `READY`

### 4. Перевірка контрольного файлу відомості
Верифікація наявності текстового файлу, створеного в домашній директорії, який містить виключно номер варіанту студента:
```bash
ssh -i ~/.ssh/ansible_key ansible@<VM1_WORKER_IP> "cat /home/student/gradebook"
```
Очікуваний вміст файлу: `12`
